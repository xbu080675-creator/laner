# Laner Product Perspective Matrix

## 目的

Laner 的功能设计不得从“我们还能做什么页面”出发，而必须从真实观赛者在比赛不同阶段想解决的问题出发。

统一公式：

```text
Feature = Persona × Match Phase × User Question
```

当前核心 Persona：

- `SPECTATOR`：普通观众 / 深度观众
- `COACH_ANALYST`：教练 / 分析人员 / 高阶复盘用户

一级 Match Phase：

- `PRE_MATCH`：赛前
- `LIVE_MATCH`：赛中
- `POST_MATCH`：赛后

同一份底层事实可以服务两个 Persona，但允许拥有不同的解释深度、信息密度和默认 UI。

---

# 1. PRE_MATCH / 赛前

## 1.1 普通观众会先问什么

1. 今天谁打谁？几点开始？现在离比赛还有多久？
2. 谁首发？有没有临时换人？
3. 两队最近状态怎么样？
4. 哪边看起来更强？为什么？
5. 哪几个选手值得重点看？
6. 最近 Rank、英雄使用和竞技状态有没有异常？
7. 这场赢了/输了会影响什么？积分、排名、晋级路径怎么变？
8. 两队以前交手谁占优？
9. 版本环境下这两队可能偏向什么 BP 和打法？
10. 去哪里看直播？比赛是“活动已经开始”还是“马上进游戏”？

### 对应产品能力

- 今日赛程 / 倒计时 / 开赛状态
- 首发阵容与变更提醒
- 选手近期 Rank / 英雄池 / 状态摘要
- 战队近期战绩、趋势、连胜连败
- 历史交手
- 积分 / 排名 / 晋级路径
- 版本与可能关注点
- 重点对位卡片
- 直播入口
- “赛事开始 ≠ 游戏开始”的赛前/赛中前置状态提示

### UI 原则

观众默认看结论，再看证据：

```text
结论：BLG 当前下路对线预期占优
↓
证据：近期对位数据 / 英雄池 / 选手状态 / 版本权重
↓
需要时展开原始数据
```

不得只展示一堆原始英文统计项让用户自己推导。

---

## 1.2 教练 / 分析人员会先问什么

1. 对手最近几场真正稳定的赢法是什么？
2. 首发变化会改变哪些体系？
3. 每条线的英雄池、优先级、Counter 倾向是什么？
4. 对手前 10/15 分钟的资源与动线习惯是什么？
5. 哪些选手最近状态、Rank、英雄使用发生明显变化？
6. 对手蓝红方 BP 有什么差异？
7. 哪些英雄一放出来会改变整套阵容结构？
8. 对手在哪些时间点容易出现资源冲突或兵线代价？
9. 第一条小龙、先锋、换线、巢虫等目标通常怎么处理？
10. 哪些信息是“样本不足”，不能过度解释？

### 对应产品能力

- BP 历史与英雄优先级矩阵
- 选手英雄池变化
- 蓝红方差异
- 前期资源/动线模式
- 线权与支援倾向
- 关键时间窗统计
- 队伍风格趋势
- 样本量与置信度
- 可筛选历史对局
- 对位/体系级情报卡

### UI 原则

教练模式默认看结构和可验证证据，不给“玄学预测”。所有推断必须能下钻到比赛样本和数据来源。

---

# 2. LIVE_MATCH / 赛中

## 2.1 普通观众会持续问什么

1. 现在到底谁优势？优势有多大？
2. 这个优势是怎么来的？
3. 导播没给我看的地方发生了什么？
4. 哪条线正在出问题？
5. 某个选手为什么突然落后/领先？
6. 下一波最重要的资源是什么？还有多久？
7. 谁有关键技能、召唤师技能、装备节点？
8. 这波团为什么能打/不能打？
9. 某个看起来不起眼的细节是不是很关键？
10. 比赛现在处于入场、BP、载入、局内还是局间？

### 对应产品能力

- 全局优势状态与变化趋势
- 经济 / 等级 / 装备 / 资源差可视化
- 下一关键资源计时
- 技能、召唤师技能、关键装备节点
- 线权 / 人数 / 位置 / 转线信息
- 导播盲区信息
- 异常事件提示
- 比赛状态机
- 全局 HUD
- 沙盘 / 地图态势表达

### 必须重点发现的“非导播信息”

Laner 的价值不是重复比分板，而是优先发现：

- 导播没展示；
- 导播晚展示；
- 比分板没有；
- 普通观众肉眼不容易同时注意到；
- 单个数据不明显，但组合后意义很大的信息。

例如：

- 关键英雄到 6 级但未学习大招；
- 某条线看似没死人但经验/回城节奏已经断裂；
- 一方为争资源付出了隐性的兵线代价；
- 某个召唤师技能或关键大招将决定下一波资源团；
- 表面经济接近，但关键 Carry 的装备节点存在明显错位。

---

## 2.2 教练 / 分析人员会持续问什么

1. 优势究竟来自操作、兵线、资源交换还是动线？
2. 当前资源交换是否值得？真实净收益是什么？
3. 哪一侧地图正在形成可利用的窗口？
4. 哪个选手的行为改变了全队后续动线？
5. 对方下一步最合理的选择是什么？
6. 当前阵容强势期在哪，已经进入还是正在错过？
7. 哪些资源是“必须争”，哪些应该主动放？
8. 团战前双方关键技能、装备、等级条件是否满足？
9. 某次失误是个人操作还是前序决策已经把局面逼坏？
10. 一次事件对后续 30 秒、1 分钟、3 分钟产生什么连锁影响？

### 对应产品能力

- 事件时间线与因果链
- 兵线 / 动线 / 资源交换分析
- 阵容强势期模型
- 关键技能与装备条件
- 地图区域控制变化
- 资源决策净收益
- 事件前后状态快照
- 局势沙盘
- 多事件关联分析
- 可回溯的实时分析标记

### UI 原则

教练层不是简单增加更多数字，而是：

```text
事实
→ 变化
→ 原因
→ 代价
→ 下一窗口
```

所有判断都要尽量能回到原始事件与时间点。

# 3. POST_MATCH / 赛后

## 3.1 普通观众会问什么

1. 到底为什么赢/为什么输？
2. 谁是关键人物？关键不是只看 KDA。
3. 哪一波真正改变了比赛？
4. 前面看着还均势，怎么突然崩了？
5. 哪几个细节当时直播里没看出来？
6. 这场比赛对积分、排名、晋级有什么影响？
7. 某个选手今天到底打得怎么样？
8. 这一局和上一局相比改了什么？
9. 系列赛整体走势是什么？
10. 我想快速看懂，而不是重新看完整场录像。

### 对应产品能力

- 结果与核心数据
- 关键转折点
- 优势曲线
- 关键人物与影响力解释
- 重要事件时间线
- “直播时容易漏掉的细节”回顾
- 系列赛局间变化
- 积分 / 排名 / 晋级状态更新
- AI/规则生成的中文复盘摘要
- 事件回放入口 / 状态快照

---

## 3.2 教练 / 分析人员会问什么

1. 计划和实际执行偏差在哪里？
2. 输赢的根因是 BP、对线、动线、资源、团战还是纪律性？
3. 哪些错误是偶发，哪些是重复模式？
4. 某次团战失败之前，真正的错误最早发生在什么时候？
5. 哪些决策结果虽然赢了，但过程其实不可复现？
6. 哪些资源交换长期为负收益？
7. 某个选手的失误是个人问题还是团队系统问题？
8. 蓝红方、阵容类型、对手风格变化后表现如何？
9. 下一场最应该调整哪三件事？
10. 哪些结论证据不足，不应该写进正式复盘？

### 对应产品能力

- BP → 对线 → 中期 → 团战的因果复盘
- 决策节点回放
- 重复失误模式识别
- 资源交换账本
- 选手/团队责任边界分析
- 系列赛跨局趋势
- 战术执行偏差
- 对手适应变化
- 复盘标签与可检索案例库
- 证据 / 样本 / 置信度展示

# 4. 功能开发判定规则

任何新功能在进入开发计划前必须填写：

```text
Persona:
- SPECTATOR / COACH_ANALYST / BOTH

Phase:
- PRE_MATCH / LIVE_MATCH / POST_MATCH

User Question:
- 用户此刻到底想知道什么？

Decision Value:
- 知道这个答案以后，用户能理解什么或做出什么判断？

Evidence:
- 需要哪些原始数据或事件？

Presentation:
- 默认结论是什么？
- 证据如何展开？

Broadcast Redundancy:
- 是否只是重复导播/比分板已有信息？
- 如果是，为什么仍有必要？

Acceptance:
- 如何证明这个功能真的帮助用户回答了问题？
```

无法回答上述问题的功能，不进入正式开发。

---

# 5. 双层信息密度原则

Laner 不需要为观众和教练维护两套底层系统。

正确方式：

```text
同一事实 / 同一事件 / 同一领域模型
            ↓
      Application Query
       ↙             ↘
Spectator View    Coach/Analyst View
```

观众层：结论优先、中文解释、低认知负担、视觉化。

教练层：证据优先、结构化、可筛选、可追溯、显示样本和置信度。

两者共享数据与业务逻辑，避免功能分叉。

---

# 6. 产品优先级原则

同等开发成本下，功能优先级依次偏向：

1. 能回答“现在发生了什么”；
2. 能回答“为什么”；
3. 能发现导播/比分板没有及时呈现的信息；
4. 能把复杂数据翻译成普通观众能理解的中文；
5. 能为教练/分析用户保留可验证证据；
6. 单纯增加更多原始数据但没有解释价值的功能优先级最低。

最终目标不是“数据最多”，而是：

> **让用户在正确的时间看到最需要知道、又最容易错过的信息。**
