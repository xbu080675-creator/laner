# INC-021-02 — TeamFightWindow 把未知 kill delta 补成 0

**状态：CONFIRMED / CRITICAL**

## 代码事实

`LiveEventDerivationService` 当前逻辑：

```kotlin
val blueKillDelta = nonNegativeDelta(...)
val redKillDelta = nonNegativeDelta(...)

if (interval <= TEAM_FIGHT_MAX_WINDOW_SECONDS &&
    (blueKillDelta ?: 0) + (redKillDelta ?: 0) >= TEAM_FIGHT_MIN_KILLS
) {
    output += TeamFightWindowEvent(
        ...
        blueKillDelta = blueKillDelta ?: 0,
        redKillDelta = redKillDelta ?: 0,
        ...
    )
}
```

`nonNegativeDelta()` 对缺失计数返回 `null`。

因此存在确定路径：
- Blue 两帧 kill 可比较并增加 3；
- Red 任一帧 kill 为 `null`；
- `blueKillDelta=3`，`redKillDelta=null`；
- 条件把 Red unknown 当 `0`；
- 最终标准事件写成 `blueKillDelta=3, redKillDelta=0`。

这不是“展示占位”，而是把未知写进 canonical MatchEvent 成为确定的 0。

## 为什么严重

Laner 明确要求：
- 缺失保持未知；
- `null` 不能补成 0；
- 无证据不能制造赛事事实；
- derived event 仍必须建立在可验证事实之上。

TeamFightWindow 是标准 Timeline 事件，一旦写入就会进入持久化、HUD 和后续分析。因此这是事实完整性问题，而不是单纯 UI 文案问题。

## 违反条款

- §3.2：业务规则必须由权威实现正确裁决；
- §6：外部/Adapter 数据不可信，权威层必须重新验证业务合法性；
- §9.1：负向/边界必须覆盖数据缺失；
- L-6：赛事状态/事实必须由统一权威层维护并保留验证语义；
- Laner Domain/Application 既有规则：nullable metric 保持 unknown，不得补 0；
- `FEATURE_BASELINE` / `SH-030`：不制造假事实 / 缺失保持未知。

## 思维过程复盘

实现 TeamFightWindow 时把“没有 delta”误当成“该侧贡献 0”，目的是允许单侧 3 杀也形成高密度战斗窗口。

问题在于：
- **已知为 0** 与 **未知** 不是同一件事；
- 只有两侧 kill total 都可比较时，`blueKillDelta/redKillDelta` 才能安全写成 Int；
- 若希望支持“一侧已知、另一侧未知”的窗口，Domain 模型必须显式允许 nullable，而不能在 Application 里偷偷降格成 0。

当前 Domain `TeamFightWindowEvent` 使用非空 Int，因此最小正确修复是：**两侧 delta 任一为 null 时，不生成 TeamFightWindowEvent。**

# INC-021-03 — 负向/边界测试没有覆盖真实缺失与 regression 情况

**状态：CONFIRMED / HIGH**

## 事实

`LiveEventDerivationServiceTest` 有：

```kotlin
fun missingOrRegressingCountersDoNotManufactureEvents()
```

但实际 fixture 只覆盖：
- 前帧 Blue/Red kills = null；
- 后帧 Blue/Red kills = null；
- gold 也均 null。

它没有覆盖：
1. **一侧可比较且 +3，另一侧 unknown** —— 正是 INC-021-02 的真实缺口；
2. **counter regression**，例如 team kills `5 → 4`；
3. player kill counter regression，例如某 player `2 → 1`；
4. 部分 player rows 缺失/不连续时，不应过度绑定 playerId。

测试名称声称覆盖 “regressing”，但代码没有真正构造 regression。

## 违反条款

- §9.1：正向、负向、边界、非目标、Bug 永久回归；
- §9.2：任务开始前必须能证明异常如何复现；
- §9.4：测试证据必须真实，不得让名称/文字超出实际执行内容；
- §2.2：测试清单与真实结果必须一致。

## 思维过程复盘

当时把“missing/null 不生成事件”视作已经覆盖了 counter invalidity 的主要风险，因此测试名顺手写成 “missingOrRegressing”。但 null 与 regression 是两种完全不同的输入形态：
- null = unknown；
- regression = 数据前后矛盾/重置/映射异常。

这种用一个宽泛测试名概括未执行场景的做法，会让后续审计误以为边界已经锁死。

# INC-021-06 — Timeline v1→v2 迁移缺少升级前可验证恢复点 / 无损 downgrade

**状态：CONFIRMED / HIGH**

## 代码事实

`JsonLiveTimelineRepository`：
- `SUPPORTED_SCHEMA_VERSIONS = setOf(1, 2)`；
- read 可读 v1/v2；
- write 永远写 `SCHEMA_VERSION = 2`；
- `atomicWrite()` 使用 `.tmp + ATOMIC_MOVE + REPLACE_EXISTING` 覆盖原文件。

这保证：
- 写入原子性；
- 升级后的当前版本可继续读取；
- v1 → v2 write-forward 有测试。

但它没有在发现目标文件为 v1 且即将首次写 v2 时：
- 创建 v1 备份；
- 保存 migration marker / recovery copy；
- 提供 v2 → v1 downgrade serializer；
- 或提供其他可验证、无损的恢复点。

LNR-021 closeout 自己也承认：若回滚到 v1-only APK，需要“备份后删除 v2 Timeline cache”。这能让旧程序重新运行，但**不能让旧程序继续读取原有 Timeline 数据**；备份的 v2 文件对 v1-only 旧 APK 仍不可读。

## 为什么属于迁移闭环缺失

这里不是要求所有 schema 都必须双向迁移，而是当前任务明确改变长期本地持久化格式，并在首次写入时覆盖旧 v1 文件。宪法要求数据/配置语义变化必须具有：
- 显式；
- 可测试；
- 可回滚 **或有恢复策略**；
- 存在数据破坏风险时在操作前建立备份/可验证恢复点。

目前只有 forward compatibility 和“删除新数据以便旧 APK 启动”的运行恢复，没有保留用户已有 Timeline 的无损恢复路径。

## 违反条款

- §7 数据、配置与迁移；
- §4 不可避免的数据格式变化必须记录迁移、测试和回滚；
- §9.1 migration rollback/recovery 的必要边界测试缺失；
- §11 compatibility/schema 文档应反映真实策略。

## 最小正确整改方向

不必做复杂双向 migration。推荐最小方案：
1. 首次将现存 v1 文件写成 v2 前，保存同目录稳定 recovery copy（例如 `.schema-v1.bak`，只创建一次）；
2. backup 本身必须通过完整 JSON decode / identity 校验后才被视为 recovery point；
3. migration write 继续使用 atomic replace；
4. 增加 v1 → backup → v2 → 验证 recovery copy 仍可按 v1 decode 的测试；
5. 明确 cleanup 策略，避免永久无限备份；
6. `COMPATIBILITY.md` 写明 forward/read/downgrade 策略。

若项目决定 Timeline 确认只是可无损重建的 cache，也必须在数据契约中正式证明/声明其可重建来源；在此之前不能用“删缓存”替代数据恢复策略。

# 4. 审计备注（暂不独立定罪）

## AUDIT-NOTE-01 — 高频全 Timeline 重派生

`LiveEventDerivationService.reconcile()` 当前每次 Current LIVE refresh 都可对完整 GameTimeline snapshot 列表重新 derive，复杂度大致 O(snapshots + events)。开发记录已识别 5s 刷新和 O(n) 复杂度，因此不直接判为违宪。

但后续真机/真实赛事验证应观测：
- 40~60 分钟比赛；
- 5s snapshot 规模；
- JSON timeline read/write；
- CPU / I/O / battery；
- reconnect / same-second replacement 时的最坏开销。

如出现明显资源问题，应再转为性能整改，而不是现在提前构建复杂增量索引。

为了同时表达“自动交付已完成但实机未完成”，创造了组合状态；实际上应该分列状态与认证。
