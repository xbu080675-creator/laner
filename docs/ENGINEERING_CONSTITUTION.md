# 通用工程宪法 / 开发强约束总规则

- **文档版本**：1.0.0-laner.1
- **规则定位**：工程唯一权威规则源（Canonical Source of Truth）
- **约束等级**：MANDATORY / MUST
- **适用对象**：人类开发者、AI、脚本、自动化工具、测试、构建与发布流程
- **适用范围**：从立项到停止维护的整个生命周期
- **最高原则**：**未满足工程宪法 = 未完成；未形成仓库记录 = 未发生。**

> 项目专属规则只能在本文件的“Laner 项目附录”中追加，不得另建互相冲突的第二套规则。

---

## 0. 最高执行条款

### 0.1 强制性
本宪法默认全部为强制规则。除非条款明确写明例外，任何人、AI、临时代码、测试代码、脚本或自动化流程均无权自行绕过。

“先跑起来”“只是小改”“以后再补”“能编译就行”“用户看不到”均不是豁免理由。

### 0.2 冲突处理
规则、需求或工程事实发生冲突时，必须停止相关实现，定位冲突，明确优先级或修订宪法，记录决策后再继续。不得静默选择其中一项。

### 0.3 违规处理
```text
发现违规 → 停止扩展 → 定位条款 → 修复或回退
→ 重跑受影响测试 → 合规复查 → 合规后继续
```

### 0.4 唯一事实源
工程事实的权威顺序为：

1. 当前目标 Git 分支、Commit、Tag 中的受控文件；
2. 本宪法及仓库内的规划、状态、规格、测试和交付记录；
3. 已留档的外部验收证据。

聊天记录、AI 记忆、旧压缩包、本地散落副本和口头约定不得替代仓库事实。

## 1. 每次开发的强制闭环

每一次新增、修改、删除、修复、重构、配置、依赖、脚本、测试、文档或构建调整，必须执行：

```text
读取最新仓库事实
→ Constitution Preflight
→ 明确任务范围与验收条件
→ 设计并评估影响
→ 最小必要实现
→ 测试与验证
→ 更新文档、状态与开发记录
→ Post-change Compliance Review
→ Commit + Push
→ 输出任务交付单
```

不适用的步骤必须标记 `N/A` 并写明理由，不得直接遗漏。

### 1.1 开发前置门禁（Preflight）
写代码前必须完整读取：

- 最新版工程宪法；
- 当前目标分支和最新提交；
- 当前开发计划与实现状态；
- 涉及模块的源码、测试与模块文档；
- 相关规范、Schema、契约、故障记录和历史交付记录；
- 必要的官方 API 与版本资料。

随后必须确认：目标、范围、责任模块、依赖方向、兼容/数据/安全影响、测试方案、回滚方式和规则冲突。Preflight 未通过不得开始实现。

### 1.2 开发后置门禁（Compliance Review）
实现后必须重新依据最新宪法和仓库事实检查：范围是否蔓延、架构边界是否破坏、依赖是否成环、行为是否无故改变、输入是否校验、测试与日志是否完整、文档与状态是否同步、结论是否有证据。

## 2. 每次开发必须留档

### 2.1 无留档不得交付
每次开发必须在同一个开发闭环内新增一份不可变的开发记录。代码已经变化但没有开发记录时，状态只能是 `DELIVERY INCOMPLETE`。

推荐路径：
```text
docs/development/YYYY/YYYY-MM-DD_<TASK-ID>_<short-name>.md
```

### 2.2 留档最低内容
每份记录必须包含：

1. 任务编号、标题、日期、负责人/执行者；
2. 需求来源与目标；
3. 开发前 Baseline（分支、Commit、版本）；
4. 本次范围与明确不做项；
5. 设计决策及原因；
6. 新增、修改、删除的全部文件；
7. 功能、架构、接口、Schema、配置、依赖和 UI 变化；
8. 测试清单、命令、环境及真实结果；
9. 风险、兼容性、安全、性能和数据影响；
10. 已知问题、阻塞项和后续任务；
11. 回滚节点与回滚说明；
12. 最终 Commit、Tag、Release 或 PR；
13. 任务状态同步结果；
14. 宪法合规结论。

禁止虚报 `PASS`、删除失败记录或把未执行测试写成通过。

### 2.3 记录不可改写历史
后续修正应新增记录，并引用旧记录；不得通过重写旧记录制造“从未失败”的历史。事实性勘误须保留修订说明。

## 3. 架构与模块边界

### 3.1 领域核心独立
Core/Domain 只能理解项目自身领域概念，不得直接依赖 UI、数据库、网络、操作系统、框架、云厂商或具体平台 API。

标准方向：
```text
Domain/Core ← Application/Use Case ← Port ← Adapter ← External Platform
```

项目不采用六边形架构时，也必须定义等价的层级、依赖方向和边界。

### 3.2 业务规则唯一
同一业务规则只能有一个权威实现。Adapter、UI、客户端和兼容层只能转换输入输出，不得复制、改写或绕过领域规则。

### 3.3 接口优先与最小公开面
跨层、跨模块访问必须通过稳定、最小的接口、Port、Service、Domain Event 或明确定义的数据模型。禁止访问其他模块的内部字段、缓存、私有状态和实现类。

### 3.4 单一职责
入口负责初始化、注册、依赖组装和生命周期连接，不得演变成 God Class。一个模块只能承担一类核心职责；复杂功能必须有明确归属。

### 3.5 依赖必须形成 DAG
禁止直接、间接和隐藏循环依赖。不得使用全局对象、Service Locator、反射、单例绕路或懒加载掩盖循环。能自动检查的架构规则必须进入构建或 CI。

### 3.6 外部能力可替换、可降级
第三方 API、AI、云服务、分析、遥测等非核心能力必须通过 Port/Adapter 接入，并声明 `SUPPORTED / DEGRADED / FALLBACK / UNSUPPORTED`。可选服务故障不得拖垮核心功能。

## 4. 范围与修改原则

- 修改必须定位责任模块并遵循最小必要变更；禁止修 A 顺便改 B、C、D。
- 未经明确批准不得进行大规模重写、改变 UI/操作习惯、公共接口、数据格式、目录结构、支持范围或兼容语义。
- 不可避免的行为变化必须记录原因、影响、迁移、测试和回滚方式。
- 禁止为未来假设提前构建没有真实需求的复杂抽象、配置或基础设施。
- 已冻结阶段只有 `BLOCKER / SECURITY / DATA LOSS / ARCHITECTURE BREAK` 可以打破；原因、影响和重测范围必须留档。
- 非阻塞事项进入 Backlog/Technical Debt，不得无限扩大当前任务。

---

## 5. API、依赖与版本

- 禁止猜测版本敏感 API。必须核对当前版本的官方资料、签名、生命周期、废弃状态、调用侧和返回语义。
- 新增或升级依赖前必须确认必要性、许可证、维护状态、安全风险、体积/性能影响和版本兼容。
- 支持范围只能由实际测试证据决定；计划支持不得描述成已经支持。
- 不兼容版本必须明确拒绝、降级或标记不支持，禁止静默硬跑。
- 锁文件必须受版本控制；依赖升级必须可追溯、可回滚。

---

## 6. 外部输入与安全边界

- 网络、客户端、UI、文件、配置、数据库、插件、脚本、Adapter、AI 工具和第三方服务输入一律不可信。
- 客户端/UI 只能提交 Intent，权威层必须重新计算权限、所有权、状态、资源、存在性和业务合法性。
- UI 隐藏不等于权限控制；所有敏感操作必须在权威层再次校验。
- 密钥、Token、密码和证书不得进入 Git、日志、截图、测试夹具或交付包；使用环境变量或正式 Secret Store。
- Debug/Admin 能力必须与普通路径隔离，默认关闭，并有审计记录。
- 安全问题不得静默降级为普通 Bug；必须标注风险等级和处置状态。

---

## 7. 数据、配置与迁移

- 长期持久化数据必须具有明确 Schema 版本。
- 存储格式不得成为领域模型；序列化和数据库结构属于 Adapter/Infrastructure。
- 数据或配置语义变化必须通过显式、可测试、可回滚或有恢复策略的 Migration。
- 写入必须考虑原子性、中断、并发、部分失败、损坏隔离和恢复；半写入不得成为合法状态。
- 非法配置必须拒绝、修正或显式 Fallback，不得产生不可预测状态。
- 数据破坏风险必须在操作前备份或建立可验证恢复点。

---

## 8. 性能、可靠性与可观测性

- 优先事件驱动、局部索引、状态变化触发和低频审计；全量轮询/扫描必须证明必要性。
- 高频逻辑必须评估复杂度、频率、最坏情况、资源占用和退化行为。
- 性能优化必须有测量证据，不得只凭感觉。
- 重要模块必须有稳定日志前缀或结构化字段，能回答发生了什么、对象是谁、来源、决策、原因和阶段。
- 禁止静默吞异常；捕获后必须记录上下文、明确恢复/降级并保持状态可预测。
- 高频日志必须限频、采样、去重或汇总；敏感信息必须脱敏。
- 错误应有稳定分类或错误码，可映射到模块、阶段、平台和操作。

---

## 9. 测试与验证

### 9.1 最低测试集合
每个变更必须根据影响覆盖：

- 正向测试；
- 负向测试；
- 边界测试；
- 非目标对照（证明没有误伤）；
- Bug 永久回归测试；
- 必要的 Unit、Contract、Integration、End-to-End、Conformance 和实机测试。

不同测试层级不得互相冒充。测试已编写、已运行、已通过、未执行、等待外部测试必须严格区分。

### 9.2 验收条件
每个任务开始前必须回答：怎么证明它工作、怎么证明未误伤、异常如何复现、什么结果算通过。

### 9.3 脚本验证
所有新增或修改的可执行脚本必须使用真实语言解析器进行语法检查；能安全试运行的必须在临时目录、Fixture、Mock、Dry-run 或 Sandbox 中试运行。解析器不可用时标记 `WAITING SCRIPT VERIFICATION`，不得宣称已验证。

### 9.4 测试证据
开发记录中必须保存测试命令、环境、输入、结果摘要和失败信息。无法在当前环境执行时写 `NOT EXECUTED` 及原因。

---

## 10. UI 与交互

- UI 不得成为业务真相来源，不得自行决定权限、余额、状态或最终结果。
- 未经需求授权不得改变现有布局和操作习惯。
- 移动端不得依赖 Hover 作为必要操作。
- 关键操作必须有明确反馈、加载态、空态、错误态和恢复路径。
- 可访问性、不同屏幕尺寸和输入方式属于验收范围。

---

## 11. 文档与故障定位

每个重要模块必须有 README 或等价文档，包含职责、输入、输出、依赖、Public API、日志、错误、测试和故障定位。

文档必须随代码在同一闭环更新；架构图、接口文档、Schema、兼容矩阵、开发计划和实现状态必须反映真实实现。

故障定位至少能够形成：
```text
现象 → 模块 → 接口/服务 → 日志/错误码 → 测试/复现
```

历史 Bug 必须进入 `TROUBLESHOOTING.md` 或等价知识库，并关联回归测试。

---

## 12. Git、分支与交付物

- 修改现有工程前必须读取当前目标分支、Commit、相关 Diff/History 和工作区状态，不得覆盖用户未提交变更。
- 每个完整开发闭环必须形成语义清晰的 Commit，并 Push 到远端；关键状态不得长期只存在于本地。
- Commit 必须能关联任务编号和开发记录。
- 阶段冻结使用 Git Tag；Tag 只能在 Definition of Done 满足后创建。
- 正式二进制、安装包和大体积产物使用 Release/制品仓库，默认不堆入源码目录。
- 构建目录、缓存、运行日志、崩溃报告、个人 IDE 状态和密钥不得成为仓库事实源。
- 压缩包只用于临时交接；恢复 Git 工作流时必须先对齐分支并检查 Diff。

---

## 13. 状态、规划与 Definition of Done

### 13.1 标准状态
只使用真实状态：`TODO / IN PROGRESS / TESTING / WAITING EXTERNAL TEST / BLOCKED / DONE / DEGRADED / UNSUPPORTED / BACKLOG`。

### 13.2 状态自动同步
任务状态变化必须在同一开发闭环同步到所有权威载体：开发计划、实现状态、里程碑摘要、看板/规划表及其统计。状态不一致时不得宣称完成。

### 13.3 DONE 定义
只有同时满足以下条件才可标记 `DONE`：

- 实现完成且范围内需求满足；
- 必要测试实际通过；
- 无未解决 P0/BLOCKER；
- 架构、安全、数据、兼容和性能检查完成；
- 文档、开发记录和故障资料同步；
- 外部/实机验收完成（如要求）；
- 任务状态及统计同步一致；
- Commit + Push 完成并有可回滚节点；
- Post-change Compliance Review 通过；
- 任务交付单完整且真实。

## 14. 审计与回溯

- 每个里程碑进入下一阶段前执行一次范围明确的全量审计并留档。
- 工程宪法发生实质性变化时，必须标记 `MAJOR / AUDIT REQUIRED`，并回溯可能受影响的历史产物；纯排版/措辞调整可标记 `SUPPLEMENTAL / NO FULL AUDIT`。
- 会话过长、换会话、AI 重新接手或临时决策过多时，必须审计这些决策是否已写回仓库。
- 审计开始前必须记录 Trigger、Scope、Baseline、权威资料和已知风险。
- 历史 PASS 不自动等于当前 PASS；必须区分历史证据、当前审计结果和正式认证。
- 审计可把当前认证从 `DONE` 调整为 `TESTING / COMPLIANCE REVIEW / BLOCKED`，但不得删除或篡改历史记录。
- 小型且边界明确的问题执行定向审计；无法证明隔离时扩大审计范围。
- 审计修复仍须走普通开发闭环，审计本身也受本宪法约束。

## 15. 固定任务交付单

每次开发完成后，必须在开发记录末尾填写：

```text
【任务交付单】

1. 任务：<ID / 标题 / 最终状态>
2. Baseline：<分支 / 开始 Commit / 结束 Commit>
3. Constitution Preflight：PASS / FAIL
4. 涉及模块：<真实模块名>
5. 强相关条款：<条款号>
6. 文件变更：
   - 新增：<逐文件；无则写无>
   - 修改：<逐文件；无则写无>
   - 删除：<逐文件；无则写无>
7. 实现内容与设计原因：<内容>
8. 测试覆盖：
   - 正向：PASS / FAIL / N/A
   - 负向：PASS / FAIL / N/A
   - 边界：PASS / FAIL / N/A
   - 非目标对照：PASS / FAIL / N/A
   - 回归：PASS / FAIL / N/A
   - Integration / E2E / 实机：PASS / FAIL / NOT EXECUTED / WAITING EXTERNAL TEST / N/A
9. 脚本验证：<逐脚本 Parser 与 Safe Trial Run；无则 N/A>
10. 日志与故障定位：<前缀/字段、首查模块、接口、错误码>
11. 影响评估：<架构/兼容/数据/性能/网络/安全/UI>
12. 已知问题与后续：<内容；无则写无>
13. 回滚：<Commit/Tag 与步骤>
14. 状态同步：<各权威载体同步结果>
15. Commit / Push / PR / Release：<结果>
16. Post-change Compliance Review：PASS / FAIL
17. 最终结论：DONE / DELIVERY INCOMPLETE / BLOCKED
```

任何字段不得虚构。缺少证据时必须使用真实的未完成状态。

├─ DEVELOPMENT_PLAN.md

## 17. Laner 项目附录

### L-1 功能冻结、底层重做
Laner 是现有电竞观赛助手的下一代重构工程。重构期间，**功能、核心用户行为和既有可见能力原则上冻结，不得因新架构而缩水、删除或静默改变**。

新工程允许并要求重做底层架构、模块边界、数据流、状态管理、缓存/持久化、网络、数据源适配、事件机制、日志、错误处理、测试和构建体系。

### L-2 旧工程仅作为行为基线，不作为代码模板
旧工程用于回答“现有产品已经能做什么、用户看到什么、什么行为必须保留”。除非经过审查证明符合新宪法与新架构，否则不得把旧代码直接复制进 Laner。

正式业务迁移前，必须从旧工程形成一份可验收的 `FEATURE_BASELINE.md`，逐项记录功能、入口、数据、交互、成功表现和测试方法。

### L-3 快速开发不得降低质量门槛
允许高速度推进，但不得通过跳过架构、测试、日志、开发留档、文档同步、Commit/Push 或合规复查换取速度。

> **快来自需求已确定、架构清楚和减少返工，不来自少做质量步骤。**

### L-4 数据源必须可替换
赛事官网、微博、OCR、第三方 API、AI 分析或其他数据源不得直接成为 UI 或领域层依赖。数据源属于 Adapter，并通过统一契约进入标准化数据层。

### L-5 UI 不与数据源直接耦合
任何页面/HUD 不得直接调用具体赛事官网、微博、OCR 或 AI Provider。UI 只消费应用层公开状态/查询结果并提交 Intent。

### L-6 赛事状态必须由统一权威层维护
“赛事开始、选手入场、BP、游戏载入、局内、局间、比赛结束”等状态不得由多个页面各自推断；必须由统一 Match/Event State 能力维护，并保留来源、置信/验证状态和时间信息。

### L-7 开发记录编号
Laner 正式任务编号默认使用 `LNR-###`。初始化阶段从 `LNR-000` 开始。若以后调整编号规则，必须先更新本宪法和开发计划。

### L-8 日志与错误码
稳定日志前缀使用 `[Laner:<Module>]`；错误码应至少可定位到 `模块 / 阶段 / 操作`，涉及外部源时还应能定位来源。

## 最终不可绕过原则

> **未读最新仓库事实，不得开发。**

> **无 Preflight，不得写代码。**

> **无测试证据，不得宣称通过。**

> **无开发留档，不得交付。**

> **无状态同步，不得标记 DONE。**

> **无 Commit + Push，不具备远程恢复能力。**

> **平台层负责翻译，权威层负责裁决。**

> **模块依赖必须为 DAG。**

> **聊天不是工程记忆，仓库才是。**

> **代码写完不叫完成；代码在规则与证据下被证明可以留下，才叫完成。**
