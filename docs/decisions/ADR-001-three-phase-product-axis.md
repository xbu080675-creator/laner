# ADR-001 — 赛前 / 赛中 / 赛后作为一级产品与架构分类轴

- 状态：ACCEPTED
- 日期：2026-09-12

## Context

Laner 是现有电竞观赛助手的下一代重构工程。用户明确要求：无论哪个页面，全部以赛前、赛中、赛后为基准。

如果只在 UI 上做三个 Tab，而底层页面、查询、状态和数据仍按功能随意增长，会重新形成旧工程式横向耦合，因此该要求必须上升为全系统一级分类轴。

## Decision

Laner 采用三个一级业务阶段：

- `PRE_MATCH` / 赛前
- `LIVE_MATCH` / 赛中
- `POST_MATCH` / 赛后

所有用户可见业务页面、主路由、HUD、功能入口、赛事查询与展示必须先归属到其中一个阶段。

共享能力（设置、搜索、Team/Player 基础资料、数据源、缓存、AI/OCR、日志诊断等）可以跨阶段复用，但不是第四个业务阶段。

比赛阶段必须由统一 Match State 映射产生，UI 不得自行判断。

## Consequences

正向影响：

- 产品结构稳定；
- 页面扩展时不易失控；
- Match State 与 UI 路由天然一致；
- 同一功能跨阶段可共享业务能力而不复制规则；
- 后续功能迁移可逐项标注阶段并做完整性审计。

代价：

- 旧功能基线提取时必须给每项功能标注阶段；
- 跨阶段能力需要区分领域复用与展示入口；
- 状态机必须有细状态到三阶段的稳定映射。

## Rejected Alternatives

### 按“赛程 / 数据 / 分析 / 设置 / 直播”等功能做一级导航
拒绝原因：功能类别会不断增长，无法表达比赛生命周期，也容易让实时和历史能力混在一起。

### 只在首页放赛前 / 赛中 / 赛后三个入口
拒绝原因：如果路由、状态和 Application 层不遵守同一轴，UI 只是表面分组，底层仍会继续耦合。

## Validation

后续 LNR-001 功能基线提取必须为每个用户可见功能增加 `Phase` 字段；LNR-003 架构冻结必须检查所有业务模块、路由和 Match State 映射是否满足本 ADR。
